# 看板（多人協作模式）

「看板」不是辦公室裡的某一位員工，是一種**工作模式**：把一個複雜任務交給整個團隊，而不是某一個人。
派給它的任務會先變成一場會議（全隊表態＋辯論），收斂成 `spec.md`，再拆成一塊 `board.json`，最後分工做完、開 PR。
它的行為規則寫在 `../backend/personas/kanban.md`（成員表、`board.json` 欄位全表、NEVER 清單都在那裡，本文只摘要）。

**本文每條機制都標了兩種記號，請先看懂差別**：

- **【程式強制】**＝後端或工具層真的會檢查／攔截，違反就失敗。
- **【提示詞約定】**＝只寫在人設裡，靠主持人自律。**違反時沒有任何東西會報錯**，你也不會收到警告。

哪些是哪些，見下面「約定 vs 強制」那張表——那是本文最該看的一節。

## 一分鐘看懂

```
 [老闆派工＋選人數]
        │
        ▼
  開會（第一輪 → 第二輪辯論）→ spec.md → board.json
        │
        ▼
 ┌──────────────────────┐
 │ ◆ 停點：等老闆說「開工」 │   ← 唯一的停點（提示詞約定，沒有程式強制）
 └──────────────────────┘
        │
        ▼
  推進循環（挑相依已滿足的票 → 派工 → 收件 → 更新板子）
        │
        ▼
  收板 → 開 PR ──► [老闆審批卡：准 / 駁回 / 300 秒不理＝自動拒絕]
```

`◆` 與 `[...]` 是老闆會被叫到的地方，其餘都是主持人自己跑。

## 老闆怎麼用

### 開一場協作

1. **從名冊選「看板」**。它跟員工同列，但不是人（`npc: false`），所以派工框的措辭不一樣。
2. **選參與人數**。這個選單**只有看板會出現**，上限等於名冊上實際的員工數（`npcs()`，**不含看板自己**），不寫死（`web/index.html` 的 `crew`／`crewN`）。
3. **寫任務**。要在真實 repo 上動手就一併選 repo，橋會把它掛成 worktree 再附一行給主持人。
4. 送出後畫面上你不會看到「看板」這個角色走動（見「限制與不做」）。

**人數是怎麼變成「【協作限制】」那一行的**【程式強制】：外殼只送一個整數 `people`，橋驗 `1 ≤ people ≤ 名冊人數`（不含看板本身），
再由 `with_headcount()` 在任務文字後面**附加**一行。措辭在橋裡，不在前端。例如選 3 位，主持人收到的是：

> 【協作限制】這次最多找 3 位成員參與（不含你這位主持人）。人選由你判斷，但總數不得超過這個數。

選 1 位時附的那一行不一樣：直接說「不必開會，直接請他給意見」，但 `spec.md`、`board.json`、停一次問老闆照舊。
人數只在正常派工時套用，`approve`／`reject`／`/stop`／`/steer` 不套（`backend/main.py:5961-5965`）。

### 流程七步

| # | 誰在動 | 做什麼 | 你會看到 |
|---|---|---|---|
| 1 | 主持人 | 判斷這題需要誰，背景派第一輪（一批最多 3 人） | 被點到的同事起身入座、頭上冒泡泡 |
| 2 | 主持人 | 第二輪辯論：讓每個人讀過第一輪全部發言再回應 | 同一批人第二次上工 |
| 3 | 主持人 | 收斂成 `spec-<主題>.md`：決議／不做什麼／任務拆解／未決 | 工作區多一個檔 |
| 4 | 主持人 | 把任務拆解落成 `board.json` | 看板面板出現四欄卡片 |
| 5 | **老闆** | **停點**：主持人問「板子開好了，共 N 項、關鍵路徑是 X→Y→Z，要開工嗎？」 | 收件匣多一張「板子開好了，主持人在等你說開工」 |
| 6 | 主持人 | 推進循環：挑相依已全部 `done` 的票派出去，一收到就改板子 | 卡片在四欄之間移動（按 ↻ 更新） |
| 7 | 主持人 | 收板、commit 交付物、呼叫 `open_pull_request` | 審批卡跳出來 |

> 第 5 步**通常**會停，但那只是約定。收件匣那張「等開工」的卡，條件是主持人這一輪的回報
> 狀態為 ok **且回報文字或最近三則事件裡含「開工」字樣**（`backend/main.py:4978-4982`）。主持人忘了寫這兩個字，
> 卡就不會出現；它若自己接著做下去，也沒有任何東西會攔。按下「開工」送出的是一句固定文字。

### 中途：審批、插話、中止

| 時機 | 你會看到什麼 | 你能做什麼 | 不理會會怎樣 |
|---|---|---|---|
| 板子開好（第 5 步） | 收件匣一張「等開工」卡 | 按「開工」，或自己打字補指示 | **沒有逾時**。它就一直等著（約定，非強制） |
| 高危操作要審批 | 員工走到你房門口擺 phone、頭上倒數餅圖、收件匣按剩餘秒數排序 | 准／駁回（可附理由） | **預設 300 秒＝自動拒絕**（`CLI_APPROVAL_S`，`backend/main.py:4328` 與 `4689-4698`；環境變數 `OFFICE_CLI_APPROVAL_S` 可調），工具整個沒執行 |
| 工作進行中你想補話 | 輸入框照常可打字 | 直接送＝自動轉成 `/steer`，**下一輪生效**（不會打斷當前那一步） | 沒事，只是它收不到你的想法 |
| 想叫停 | 按中止 | 收卡、清審批、釋放工位 | 它會跑到自己收工 |

**中止在兩種引擎上行為不同**，這是同一顆按鈕最容易誤判的地方：

- **cogito**：POST `/stop`，語意是「**這一步跑完之後**停」——不保證當場殺掉子 agent。（若它正卡在審批，橋會先替你送一個 `reject` 再 `/stop`，免得它在那裡等到逾時。）
- **Claude Code**：`kill_tree()`，**連子孫行程一起砍**（MCP 伺服器、背景指令⋯），`backend/main.py:5817`。

兩條路都會走 `force_stop()` 收掉畫面上的卡。另外 persona 裡那句「子 agent 不會被殺」講的是
`subagent_await` 逾時的情形，跟你按中止是兩件事，不要混在一起看。

## 背後的架構

### 主持人＋子 agent：星狀，不是鏈狀

```
   小美(PM)   老徐(CTO)   阿哲(後端)   老王(UI)
       └──────────┴─────┬─────┴──────────┘
                        │
                看板（主持人）
                        │
       ┌──────────┬─────┴─────┬──────────┐
   小葵(前端)  阿海(DevOps)  小樺(研究)   …
```

（名字依你自己的名冊，這裡以預設團隊為例。）

主持人在中心，子 agent 全部掛在它底下。**子 agent 彼此看不見**，也不互相傳話——每個人的輸入只有
主持人寫的那段 prompt，輸出只回給主持人。所以：

- 共享的狀態只有**同一個工作目錄**（`meeting*.md`、`spec*.md`、`board*.json` 與 repo worktree）。
- 要他讀的檔**給路徑、不貼內容**：子 agent 讀得到同一個工作區，貼進去等於同一份內容付兩次輸入費。【提示詞約定】
- 成員名單與「找他問什麼」是從團隊設定自動產生的（見 `team-setup.md`），不是寫死在人設裡。

### 兩輪辯論為什麼存在

因為星狀拓撲有一個盲點：第一輪收齊的「三人同向」，可能是真共識，也可能只是三個人各自推出同一個答案——
**不逼他們互相看過，分不出這兩種**。所以第二輪的 prompt 只給 `meeting.md` 的路徑和三個問題：
「別人哪一點說服了你、你改了什麼」「哪一點仍然不服」「只能保留一條決議是哪條」。

兩輪就停。還有分歧就原樣寫進 spec 的「決議（A vs B，選 A，因為…）」或「未決」，讓分歧那條線看得見，
而不是被主持人一個人抹平。每收到一份發言就立刻 append 進 `meeting.md`、**原話不改寫**——改寫過就沒有稽核價值。【提示詞約定】

### 排程與並行

主持人的推進循環只有一條規則：**挑相依已全部 `done` 的票**，背景派出去，一有人交件就回頭重算一次。
派出去的當下就把票改成 `doing` 並寫上 `owner`，不等收工才補——看板要能回答「現在」，不是「剛才」。

一批最多 3 人並行。**pixel-office 後端沒有這個檢查**，它是引擎自己的併發上限；人設裡那句「超過會被擋」
指的是引擎，不是辦公室。【提示詞約定】

派工綁了 repo 時還有一條：**一個檔案只能有一個人寫**。子 agent 共用同一份工作樹與同一個 git index，
兩個人同時改一個檔就是後寫的整份蓋掉前面的，而且**不會有任何錯誤訊息**，git 這時也幫不上忙（只有一份工作樹，
沒有兩個版本可以比）。所以派之前要先確認這一批人要碰的檔案沒有交集，判斷不了就讓子 agent 只調查、由主持人動手寫。【提示詞約定】

### board.json：面板是投影，不是編輯器

`board.json` 由主持人寫、人只看。`board_file()` 決定哪塊板是「現在這塊」：`board.json` 優先，
否則取 `board-<主題>.json` 裡 mtime 最新的；`board.<時間>.json` **刻意排除**（那是封存名）。

**`status` 只有三種，但面板顯示四欄。**

| 面板欄位 | 來自 | 說明 |
|---|---|---|
| 待辦 `todo` | `status` | 相依都滿足了、還沒人做 |
| **等待相依 `blocked`** | **算出來的** | `board_column()`：`todo` 且 `deps` 還沒全部 `done`。**這不是一種 status**，主持人不該自己寫 |
| 進行中 `doing` | `status` | 有人正在做 |
| 完成 `done` | `status` | 做完了，`out` 填產出檔名 |

少一個要維護的狀態，就少一種標錯的可能。欄位只有 `task` 與 `tasks[]`（`id`／`title`／`deps`／`status`／`owner`／`out`），
全表見 `../backend/personas/kanban.md` 的「上板」一節。

其他事實：

- **面板唯讀**【程式強制】：`/office/board` 只有 `GET` 與 `DELETE`，**沒有任何寫入端點、沒有拖拉**。唯一的互動是 ↻（agent 寫檔時橋不會知道）。
- **🗑 收掉＝封存，不是刪檔**【程式強制】：`DELETE` 會把檔 rename 成 `board.<時間>.json`，一次協作的完整紀錄留在工作區。封存的板子不會再被標成「進行中」。
- **封存的板子可以回看**：面板附一份封存清單，點進去走 `GET /office/board?f=<board.時間.json>`（只吃清單裡的白名單），再按「↩ 回到目前」回到現在這塊。
- **沒有鎖、沒有版本號、沒有並發控制**。「只有主持人能寫 board.json」是約定——子 agent 真的去寫，不會有任何東西阻止。【提示詞約定】
- 還沒上板時，面板退回顯示會議進度（這一輪派了誰、回來幾個）。

### 為什麼 PR 一定要經老闆審批

員工的 Bash 在沙箱裡、沒有網路，也讀不到老闆的 `gh` 登入。所以推分支與開 PR 包成一顆 MCP 工具
`mcp__office_git__open_pull_request`，跑在沙箱外、以老闆身分執行，但邊界全部在工具裡驗，不靠模型自律【程式強制】：

- `repo_dir` 必須在員工工作區底下、而且是 git worktree 的根；
- 當前分支必須是 `office/…`（不碰 `main`、不碰老闆自己的分支）；
- 追蹤中的檔都已 commit（沒 commit 就 `ToolError` 直接擋掉），而且比預設分支多出 commit；
- 只 push 這一條分支、不 force；同一條分支已有 PR 就回那一個，不重開。

**它刻意不放進常駐許可**：每次呼叫都會跳審批卡。駁回或 300 秒逾時的時候，PermissionRequest hook 回 `deny`，
**工具整個沒執行**；而 `git push` 排在審批之後（`backend/tools/office_git_mcp.py:86`），所以結果是
**PR 沒開，分支留在本機 worktree、未推遠端**。commit 還在，你隨時可以自己推。

回傳裡的 **`not_in_pr` 是未追蹤檔清單**（`git ls-files --others --exclude-standard`，上限 50 筆），
不是「沒進這個 PR 的檔」。正常情況它列的是刻意不進 repo 的會議檔（`meeting*.md`／`spec*.md`／`board*.json`）；
**除了會議檔之外還有別的，就是漏 commit 了交付物**。已追蹤但沒 commit 的改動不會出現在這張清單上——那種情形工具根本不會跑到這一步。

## 哪些是硬限制：約定 vs 強制

| 機制 | 哪一種 | 違反／不照做時會發生什麼 |
|---|---|---|
| 參與人數上限（【協作限制】那一行） | 【程式強制】驗 `1 ≤ people ≤ 名冊人數`（`npcs()`，不含看板本身），`with_headcount()` 附加（`backend/main.py:5961-5965`） | 超出範圍的數字送不出去。但**主持人實際找幾個人沒有檢查**，那一行只是文字 |
| 面板唯讀、不能拖卡 | 【程式強制】只有 `GET`／`DELETE` | 沒有寫入的路可走 |
| 🗑 收掉＝rename 成 `board.<時間>.json` | 【程式強制】 | 檔案不會被刪 |
| `blocked` 由 `deps` 算出來 | 【程式強制】`board_column()` | 主持人自己寫 `status: "blocked"` 不是三種合法值，面板**不報錯、靜默改判**成 `todo` 或 `blocked` |
| PR 一定經審批、分支／工作樹檢查 | 【程式強制】工具層攔截 | 條件不符就 `ToolError`，push 不會發生 |
| 審批逾時＝自動拒絕 | 【程式強制】`CLI_APPROVAL_S` 預設 300 秒，環境變數 `OFFICE_CLI_APPROVAL_S` 可調（`backend/main.py:4328`、`4689-4698`） | 你沒看到那張卡，等於你拒絕了。（`main.py:949` 的 `APPROVAL_DEFAULT_S` 只管倒數徽章怎麼畫，調它不會改變逾時） |
| Codex 引擎跑看板 | 【程式強制】派工直接被擋（`backend/main.py:5854`） | 回「看板暫不支援 Codex 引擎」，請改選別的 |
| **「板子寫好停一次問老闆」** | **【提示詞約定】零強制** | 收件匣那張卡只靠回報文字含「開工」字樣猜（`backend/main.py:4978-4982`）。主持人一路做完也不會被攔 |
| 只有主持人寫 `board.json` | 【提示詞約定】檔案沒有鎖、沒有版本號 | 兩個人同時寫就互相蓋掉，**沒有任何錯誤訊息** |
| 一個檔案只有一個人寫 | 【提示詞約定】 | 後寫的整份蓋掉前面的，**不會報錯**，也看不出少了什麼 |
| 一批最多 3 人並行 | 【提示詞約定】pixel-office 不檢查 | 上限來自引擎本身，不是辦公室 |
| 兩輪辯論、逐字稿原話不改寫、`meeting.md` 邊收邊寫 | 【提示詞約定】 | 主持人少開一輪、改寫發言，都不會有人知道 |
| 會議檔不進 repo（只 `git add` 交付物） | 【提示詞約定】 | 誤 `git add -A` 的話會議檔就進 commit 了，工具不擋（它只擋「沒 commit 的改動」） |

## 限制與不做

- **看板沒有身體**：它在名冊上，但不走位、不入座、不掛台詞泡泡，鏡頭追人時也被濾掉。畫面上只會看到被它派出去的同事在動。
- **Codex 引擎跑不了看板**：主持人要派子 agent，那個引擎還沒接，派工當場被擋。cogito 與 Claude Code 都可以，但中止行為不同（見上）。
- **沒有「暫停／回上一步」**：流程只有一個停點（第 5 步），而且是約定。想改方向就用插話（下一輪生效）或中止重派。
- **面板不是編輯器**：你不能在畫面上改票、改相依、改 owner。要調整就跟主持人說。
- 本文不講安裝、啟動與引擎設定（見 `../README.zh-TW.md`），也不講團隊設定與工位（見 `team-setup.md`）。
- 成員表、`board.json` 欄位全表、spec 範本與完整 NEVER 清單都不在這裡重貼，請直接讀 `../backend/personas/kanban.md`。
